# Propagation: broadcast, announce and fetch as pure functions, and the intake bounds

Lines are `XDCIndia/go-ethereum` at `6fc8e8c2`. Rust: `xone_builder::txpool::propagate`. No sockets, no timers: the functions take the peers' state and the time and return [`Effect`]s (`Transactions`, `Announce`, `Fetch`) for the caller to put on the wire.

**Rule: sending.**

1. The pool's new executable transactions (`Pool::take_new`, geth's `NewTxsEvent`) are sent by `BroadcastTransactions` (`eth/handler.go:770-824`): for each transaction not known to a peer, the `ceil(sqrt(n))` peers with the lowest score receive it whole, the others receive its hash (`choosePeers`, `:1000-1030`; the score is a keyed hash of the node, the peer and the sender, so one sender's transactions go to the same peers). A transaction over 4,096 bytes is never sent whole, only announced (`txMaxBroadcastSize`, `:68`). Everything sent or announced is marked known to that peer (`knownTxs`, bounded to 32,768, `eth/protocols/eth/peer.go:40`). Per peer the queue of whole transactions and the queue of announcements each keep at most 4,096 hashes, oldest dropped (`broadcast.go:81`, `:185`); a packet of whole transactions is closed when it holds at least 100 KiB (`maxTxPacketSize`, `broadcast.go:28`, `:50`), an announcement at about 3,200 hashes.
2. **XDC wire peers get no announcement.** On eth/100 and eth/101 code 0x08 is the legacy `OrderTxMsg`; geth marks the hashes known and sends nothing (`peer.go:380-398`). So a transaction reaches a XDC-wire peer only if the peer is among the `ceil(sqrt(n))` chosen for that sender. `propagate::broadcast` does the same for `Wire::Full` peers (marks known, no message).
3. **A new peer.** geth announces the pool's pending hashes (`eth/sync.go:26-38`); on eth/100 and eth/101 that call is the no-op above, so a XDC peer that connects never learns the pool. **xOne decision (not parity):** `sync_new_peer` sends a `Wire::Full` peer the pending transactions whole (packets of at least 100 KiB) and a `Wire::Announce` peer the hashes. It adds only messages, no rule: it is the re-emit-to-new-peers lesson of xOneGo `ce79ac6f`, since a sign transaction dropped while a peer was away would otherwise never reach it. The owner may want to bound it (rate, size) before the devnet run.

**Rule: receiving announcements.** `Fetcher` is `TxFetcher` (`eth/fetcher/tx_fetcher.go`) as a state machine (`notify`, `tick`, `delivered`, `drop_peer`, `next_deadline`):

1. A hash the pool already has is not tracked (`Notify`, `:273-343`; the caller passes `known`).
2. A peer may have at most 4,096 hashes outstanding; a batch is cut to fit, and a peer at the limit is ignored (`maxTxAnnounces`, `:43`, `:575-600`).
3. A new hash waits 500 ms (`txArriveTimeout`, `:71`; `txGatherSlack` 100 ms, `:75`) for the transaction to arrive by broadcast, because most do (`:725-760`). If it does arrive (`delivered`, `direct` false) the wait ends and nothing is fetched.
4. Then it is requested from a peer that announced it: one request in flight per peer, at most **256 hashes and 128 KiB of announced bytes** in a request (`maxTxRetrievals`, `maxTxRetrievalSize`, `:53`, `:59`; `scheduleFetches`, `:1108-1180`, in the order announced, which tends to keep nonces in order; the size test runs after the count test, as there). geth picks peers in map order; this picks by peer id.
5. A request not answered in 5 s (`txFetchTimeout`, `:89`; `:761-806`) moves its hashes to the other peers that announced them, keeps the request as dangling so that a late answer is recognised, and the slow peer is not asked again for those hashes.
6. A delivery that disagrees with the announcement (another type, or a size off by more than 8 bytes) names the peer to drop (`:808-948`). A reply that omits hashes before its last delivered hash drops the announcing peer from those hashes; a reply that delivers nothing is not retried.
7. `drop_peer` (`:949-1030`) returns its hashes to the other announcers.

**Not ported.** The set of recently underpriced hashes (32,768 entries, 5 minutes, `:62-67`, `:344-363`) and the cache of hashes of recent blocks' transactions (`txOnChainCacheLimit`, `:83`): the caller passes both as `known`. Blob transactions. The announce packet's version-specific fields (eth/72 sizes, custody mask).

**Rule: intake bounds (ADR-007).** `Intake` admits one transaction at a time against Q5 (per peer: 128 transactions, 1 MiB) and Q6 (all peers: 4,096 transactions, 8 MiB in admission, i.e. decode and sender recovery): over either is rejected, not scored (a sustained excess is the peer token bucket's, Q10). `done` releases an item when it has left admission. The constants are copies of `xone_node`'s ADR-007 table: `xone-builder` is a lower layer than `xone-node` (`ci/layering.py`), so it cannot import `BoundedQueue` or `PeerBudget`; the node wires `Intake` in front of `Pool::add_raw`.

**Vectors.** `crates/xone-builder/tests/propagate.rs`: fan-out to `ceil(sqrt(n))` and stability per sender, XDC wire peers get no announcement, large transactions announced only, queue caps and packet size, new-peer sync, 500 ms wait then one request per peer, 256 hashes and 128 KiB per request, 4,096 announced hashes per peer, 5 s timeout to an alternate announcer, delivery checks, drop. `tests/rules.rs`: `intake_rejects_past_the_adr_007_bounds_without_scoring`. `tests/flood.rs` puts 100,000 transactions through `Intake` and the pool.

**Not covered.** The 3-node devnet check that a transaction submitted on node A reaches node B's pool within 2 s p99 (#36 acceptance gate 5): it needs the node wiring (RPC XB-22, the peer set, `xone-node`) and a devnet run. With the pin's rule above, two peers each give `ceil(sqrt(2)) = 2` direct recipients, so a 3-node devnet needs no relay; the latency is the wire's and the pool's `add_batch`, which is tens of microseconds per transaction in the flood (see the report).
