# ADR-002: Integration option and dependency diversity (SDK, crates, adapter or fork, Go)

* Status: **Proposed**. It stays Proposed until the owner accepts it (issue XDCIndia/xOne#8, rollback rule).
* Date: 2026-11-11
* Pins: xOne `main` `2e77a4cf516c23a5fd5d7c5421a41d7a58a02dd1` plus branch `feat/xa-03-adr-002-net-spike`; geth-XDC oracle `XDCIndia/go-ethereum` `6fc8e8c2088b7f18264f5663036669d04fa7becf`; revm `=43.0.3`; reth `v2.3.0` `9384bc53d8c0c77e59cac83fdaaf3b372c6d2216` (lower crates only), `v2.8.1` `d763342fa185e4e90ee79dc65f6a5706168b0bcb` and `v2.10.1` `58ebce14ae63dab040beae301e1578cd0dc55e8a` (read, not built into the workspace).
* Evidence: `spikes/wide-balance/REPORT.md` (XA-02), `spikes/net/REPORT.md` (S2), `spikes/sdk-leaf/REPORT.md` (S3).
* Names: the issue calls the options (a) to (d). Plan R4 calls (a) "B, reth SDK", (b) "C, standalone workspace with pinned libraries", (c) "A, fork reth" with a smaller scope, and R5 calls (d) "Go on geth packages".

## Decision

**Choose (b): a standalone workspace that uses selected crates as pinned libraries.** This confirms the default of plan R4 (option C) with these exact terms:

1. **EVM: revm `=43.0.3` from crates.io, with the XA-02 journal wrapper (option B of XA-02).** `account-ext` is not enabled. Zero revm patches.
2. **State, trie leaf, account type and snap bodies are ours** (`xone-state`, `xone-net`). `alloy_trie::HashBuilder::add_leaf` takes encoded bytes, so the wide balance goes through (XA-02). `alloy_trie::TrieAccount` is used for genesis only.
3. **Network: `reth-ecies` and `reth-network-peers` only, by git revision, unmodified.** Everything above RLPx is ours: Hello and capability matching, snappy, Ping/Pong, the eth/100 and eth/101 message set, `xdpos2` messages, snap/1, session and peer management, and (to be decided in M5) discovery. `reth-eth-wire`, `reth-network`, `reth-trie`, `reth-provider`, `reth-evm`, `reth-chainspec` and `evm2` are on the deny list of the M0 dependency check.
4. **Pin today: reth `v2.3.0`.** It is the newest tag whose `rust-version` (1.93) the workspace toolchain `1.94.0` accepts. Move to `v2.8.1` or later when the toolchain is raised to 1.95 or 1.96; the `ecies` and `peers` API used here is the same (S2: `v2.8.1` to `v2.10.1` changed 1 line).
5. **Fallback for the transport pin:** vendor `reth-ecies` (1,686 lines at `v2.8.1`, MIT or Apache-2.0) into `xone-net` with its licence notice. Do this only if the git source is unavailable or the MSRV gap blocks the toolchain, not before.

Why not the others, in one line each: (a) cannot carry the wide balance without a fork and has no eth/100; (c) is what reth-xdc already is and costs a rebase on every reth tag; (d) is correct but shares the oracle's code and bugs, so the seventh client would add no independence.

## Context

* reth replaced revm with `evm2` (PR #25002, merged 2026-10-24). `v2.8.1` (2026-10-23) is the last revm tag; `v2.9.0` (2026-10-29) and later use `evm2` by git revision. `evm2` is not published (`0.0.0-reserved`). "revm and reth crates" are two pins that move apart.
* alloy-trie `TrieAccount.extension` is a fifth RLP item; geth-XDC encodes the wide value inside the balance item (XA-02).
* reth's snap is snap/2 only. geth-XDC at the pin serves snap/1 (Hello of the local node: `snap/1`).
* A seventh binary is not automatically an independent failure domain (issue #8, "Why").

**Stake exposure rule.** For each domain, the exposed stake is the sum of the stake of the clients in the row. The owner fills the stake column; the domain table then gives the number. A domain whose exposed share is above the owner's tolerance needs an independent implementation or a different pin.

## revm pin strategy (reth moved to evm2)

* **Pin.** `revm = "=43.0.3"` in `xone-evm` (exact), the same pin the spike uses; every `revm-*` crate follows from `Cargo.lock`. `account-ext` is off in production. The build without it is green on the same matrix (`cargo test -p wide-balance-spike --no-default-features`).
* **Bump rule.** One PR per bump: changelog read, the corpus (#6), the XA-02 matrix and the diff-exec range all green, and a note of the revm version in the PR. No automatic bump. The M0 dependency check fails on two revm majors in the lock.
* **The two pins no longer interact.** The reth crates in (b) are `ecies` and `peers`. At `v2.8.1` and at `v2.10.1` their tree has 129 packages and no `revm` and no `evm2` (S2, `trees/`). A revm bump does not move reth, and a reth bump does not move revm.
* **evm2 is a watch item, not a candidate.** It is a separate repository (`alloy-rs/evm2`, Apache-2.0, last push 2026-11-10), unpublished (`0.0.0-reserved`), taken by git revision with a `[patch]` in reth `v2.10.1` (`Cargo.toml:434-437`, `:671-673`), and needs Rust 1.96. Re-evaluate only when it is published on crates.io with semver releases, two minor releases pass without a breaking change to the journal or handler API, and a branch passes the full corpus. The XA-02 wrapper (`JournalTr`, `JournaledAccountTr`, one `Handler` override) would have to be rebuilt on its API.
* **Watch revm itself.** reth was its largest downstream user and no longer exercises it. Check at each bump: release cadence (last release `v120`, 2026-09-24), the RustSec advisories, and the Ethereum state-test results. If revm has no release for six months, or an advisory stays unfixed for 30 days, the owner decides between freezing at `=43.0.3` and vendoring it unmodified. A frozen exact pin is still zero patches.
* **Count.** revm patches or forks: **0** (XA-02: no row needed a change in a revm source file). reth patches: **0** (S2 and S3 use unmodified upstream; the workaround is our own code beside it). `alloy-trie` patches: **0**. Target 0; any change to the count re-opens this ADR.

## Consequences

* M5 grows: the session layer, capability matching, Ping/Pong, eth/100, eth/101 and eth/63 message sets, `xdpos2` messages, snap/1 client and server, peer manager, and discovery. The S2 module (231 lines) is the start of the first four items. Plan change C2 chose "(b) lower crates only"; this ADR confirms it.
* The toolchain must move to 1.95 or later before reth `v2.4.0` or newer can be pinned. Until then the pin is `v2.3.0`.
* Plan risk K6 is closed by the fallback it named. K5 gets the revm text above.
* snap/1 is ours; reth and ethrex are references only (ethrex is Apache-2.0 and tied to its own storage).
* The XA-02 recommendation (option B journal wrapper) is part of this decision; falling back to option A (`account-ext`) is allowed only with the divergence of row `wide_low_zero_empty` accepted by the owner.

## Re-open trigger

Re-open this ADR, with a written choice to the owner, if any of these holds:

1. A change in a revm, `alloy-trie` or reth source file becomes necessary (the patch count above goes from 0 to 1).
2. The M2 gate is missed twice (the R5 trigger of the plan), or the XA-02 matrix finds a row the wrapper cannot express on a revm bump.
3. reth makes `EthVersion` and the capability matcher open to non-standard versions, or gives `NodePrimitives` an account type and a leaf-encoder trait, and publishes the network crates on crates.io with versions. Then (a) or a thinner own eth-wire is worth a new spike.
4. `evm2` is published and proven by the criteria above, or revm stagnates by the criteria above.
5. The owner's stake in a shared failure domain (table above) exceeds the owner's tolerance.
6. XDC adds an account or state encoding that the journal wrapper and `add_leaf` cannot express.

## Not covered by this ADR or its spikes

* A real legacy XDPoSChain peer, discovery v4 and v5, snap/1, bodies, receipts, NewBlock gossip and a validator exchange (S2 "Not covered").
* `evm2`'s journal API (S3 "Not covered"); mainnet; the upgrade cost of geth tags (option (d)).
* Stake figures and the verification of the rows marked "not re-verified".
* Owner acceptance. This record is a proposal.
